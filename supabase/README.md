# Supabase

Database schema changes for this project live in `supabase/migrations/` and follow the
[Supabase CLI](https://supabase.com/docs/guides/local-development/cli/getting-started)
conventions: one timestamped SQL file per change, applied in filename order.

`config.toml` was generated by `supabase init` and matches the local-development URL in
`.env.local` (`http://127.0.0.1:54321`). **Check `major_version` under `[db]`** against your
hosted project (`show server_version;`) before relying on `supabase start` to mirror production.

## Migrations

| File                                  | Purpose                                                              |
| ------------------------------------- | -------------------------------------------------------------------- |
| `*_stripe_webhook_idempotency.sql`    | Durable, database-enforced deduplication of Stripe webhook events.   |
| `*_stripe_subscription_lifecycle.sql` | One function for every subscription lifecycle event, with ordering.  |
| `*_subscriptions_ownership.sql`       | RLS, privileges and integrity constraints on `public.subscriptions`. |
| `*_account_activity.sql`              | Append-only, per-user history of account changes (settings page).    |
| `*_support_requests.sql`              | Authenticated support requests, own-only access and limits.             |
| `*_rate_limits.sql`                   | Per-user allowances for expensive operations (invoice exports).      |

### `stripe_webhook_idempotency`

Stripe delivers webhooks at least once. If our HTTP response is lost after a successful write,
the same event arrives again. This migration adds:

- **`public.stripe_webhook_events`** — a ledger keyed on Stripe's event id (`evt_…`). The
  primary key is the idempotency guard. RLS is enabled and all privileges are revoked from
  `public`, `anon` and `authenticated`, so it is not reachable through the REST API.
- **`public.stripe_apply_checkout_completed(...)`** and
  **`public.stripe_apply_subscription_deleted(...)`** — `plpgsql` functions that record the
  event id and apply its effect on `public.subscriptions` in **one transaction**. They return
  `'applied'`, `'duplicate'` or (for deletions) `'no_match'`. Concurrent deliveries of the same
  event serialise on the primary key: the second waits for the first transaction and then
  sees `'duplicate'`. Any failure rolls back the ledger row too, so a failed attempt never
  marks the event as processed and Stripe's retry can apply it.
- **Privileges:** `EXECUTE` is revoked from `public`, `anon` and `authenticated` and granted to
  `service_role` only. Without this, anyone holding the public anon key could call the
  functions via `POST /rest/v1/rpc/…` and forge subscription state, bypassing Stripe
  signature verification. The webhook route calls them with the service-role client
  (`src/infrastructure/supabase/admin.ts`).

The TypeScript side of the contract (function names, parameter names, result values) is
`STRIPE_RPC` in `src/features/billing/services/handle-stripe-webhook-event.ts`; a unit test
checks it against the migration file, and the integration tests exercise it against a real
PostgreSQL server.

### `stripe_subscription_lifecycle`

Replaces the two per-event functions with **`public.stripe_apply_subscription_event(...)`**,
used for `checkout.session.completed`, `customer.subscription.{created,updated,deleted}`,
`invoice.paid`, `invoice.payment_succeeded` and `invoice.payment_failed`. It also adds four
columns to the ledger (`stripe_subscription_id`, `event_created`, `type_rank`, `outcome`) and a
partial index on `(stripe_subscription_id, event_created desc, type_rank desc) where outcome = 'applied'`,
so the ledger doubles as a per-subscription timeline. Returns `'applied' | 'stale' | 'duplicate'`.

**How ordering and consistency are guaranteed** — every event runs through these steps in one
transaction:

1. **Claim** the event id in the ledger (`insert … on conflict do nothing`). A redelivery
   returns `duplicate`. Concurrent deliveries of the same event block on the primary key until
   the first transaction ends, then see `duplicate` (committed) or proceed (rolled back).
2. **Serialise per subscription** with `pg_advisory_xact_lock(hashtextextended(subscription_id))`.
   Concurrent events for one subscription execute strictly one after another, and each one
   sees the committed result of the previous. This also prevents two simultaneous "first"
   events from inserting two rows — `subscriptions` needs no unique constraint for this.
3. **Order by Stripe's timeline.** Each applied event records `(event.created, type_rank)`.
   An incoming event whose position is older than the newest applied position for that
   subscription does **not** change `status` and returns `stale`. `event.created` has second
   resolution, so `type_rank` breaks ties within a second:
   `checkout.session.completed (10) < customer.subscription.created (20) < invoice.* (25) <
customer.subscription.updated (30) < customer.subscription.deleted (40)` — the subscription
   object is the source of truth, payment outcomes are a complementary signal, checkout's
   status is only provisional. Equal positions apply in arrival order.
4. **Terminal statuses are never left.** `canceled` and `incomplete_expired` are final in
   Stripe; any event that would move away from them is `stale` regardless of its timestamp.
5. **Identity merges independently of ordering.** `stripe_customer_id` and `"userId"` are only
   ever filled in, never cleared or replaced: existing value → event metadata
   (`session.metadata.userId`, `subscription.metadata.userId`, or the invoice's subscription
   metadata snapshot) → any other subscription of the same Stripe customer that already has a
   user. A `stale` checkout completion therefore still links the user.
6. **Failure rolls everything back**, including the claim, so a failed event is not marked
   processed and Stripe's retry can apply it.

`status` receives Stripe's real statuses (`active`, `trialing`, `past_due`, `unpaid`,
`incomplete`, `incomplete_expired`, `paused`, `canceled`). Because a Checkout Session carries no
subscription status, its contribution is derived from `payment_status`
(`paid → active`, `unpaid → incomplete`, `no_payment_required → trialing`) and outranked by
every subscription event. Invoice outcomes map per Stripe's documented behaviour
(`payment_failed`: first invoice → `incomplete`, renewal/update → `past_due`;
`paid`: renewal/update → `active`; a `$0` first invoice is ambiguous and skipped).

**Stripe webhook endpoint configuration.** The endpoint must be subscribed to all of:
`checkout.session.completed`, `customer.subscription.created`, `customer.subscription.updated`,
`customer.subscription.deleted`, `invoice.paid`, `invoice.payment_succeeded`,
`invoice.payment_failed`. Other event types are acknowledged and ignored.

### `subscriptions_ownership`

Until this migration, nothing said who may read or write `public.subscriptions`. A table created
with Supabase's defaults and no row level security is readable **and writable** by anyone holding
the public anon key through PostgREST — every user's billing rows, a self-granted `active`
status, deleted or forged rows. The application always filtered by `"userId"`, but the REST API
does not go through the application. This migration makes the database enforce it:

- **Privileges.** `anon`: nothing. `authenticated`: `SELECT` only. `service_role` (the webhook):
  read/write. Re-applied on every run, so a privilege handed back by accident is revoked again.
- **Row level security** is enabled with a single policy, `subscriptions_select_own`:
  `"userId" = auth.uid()` (or the `::text` form when `"userId"` is not a `uuid` — the type is read
  from the catalog). **Every pre-existing policy on the table is dropped first**: policies are
  OR-ed, so one leftover `using (true)` would defeat the new one. There is no INSERT/UPDATE/DELETE
  policy at all, so writes are denied even if a privilege is granted back.
- **One row per Stripe subscription**: a partial unique index on `stripe_subscription_id`. It is
  created only when the table holds no duplicates; otherwise the migration raises a `WARNING`
  and continues (the lockdown still applies). Resolve the duplicates and re-run — the file is
  idempotent.
- **One owner per Stripe customer**: a `BEFORE INSERT OR UPDATE` trigger rejects a row that would
  link a customer to a second user or move it to another user (`23505`). The webhook's own
  "borrow the user from another subscription of the same customer" rule already assumed this;
  now a mis-entered Dashboard subscription fails loudly (non-2xx, Stripe retries, the ledger row
  is rolled back) instead of silently cross-linking two accounts. Customers that are _already_
  linked to several users are reported with a `WARNING` at apply time — their next webhook
  write will fail until fixed.
- **If the table does not exist yet**, the migration prints a `NOTICE` and does nothing; re-run
  it once the table exists (`supabase migration up` / re-apply the file).

Verify on the hosted database after deploying:

```sql
select relrowsecurity from pg_class where oid = 'public.subscriptions'::regclass;  -- true
select policyname, cmd, roles from pg_policies
 where schemaname = 'public' and tablename = 'subscriptions';                     -- exactly subscriptions_select_own / SELECT / {authenticated}
select r.rolname, p.priv, has_table_privilege(r.rolname, 'public.subscriptions', p.priv)
  from pg_roles r, (values ('SELECT'),('INSERT'),('UPDATE'),('DELETE')) as p(priv)
 where r.rolname in ('anon','authenticated','service_role');                      -- anon: all false; authenticated: SELECT only; service_role: all true
select indexname from pg_indexes where indexname = 'subscriptions_stripe_subscription_id_key';
select tgname from pg_trigger where tgname = 'subscriptions_customer_owner';
```

Find and resolve the data problems the migration warns about:

```sql
-- Duplicate rows for one subscription (keep the one matching Stripe; the webhook will refresh it).
select stripe_subscription_id, count(*), array_agg(status)
  from public.subscriptions where stripe_subscription_id is not null
 group by 1 having count(*) > 1;

-- One Stripe customer linked to several users (decide the rightful owner in Stripe first).
select stripe_customer_id, array_agg(distinct "userId"::text)
  from public.subscriptions where stripe_customer_id is not null and "userId" is not null
 group by 1 having count(distinct "userId"::text) > 1;
```

The application side is defensive too: `getSubscriptionOverview` refuses to pick a Stripe
customer for the Customer Portal when a user's own rows are ambiguous (several customers, a live
subscription without one, or one subscription naming two customers), and shows a subscription
whose rows disagree as "needs review". What it cannot detect is a customer shared across _two
users'_ rows — reads are user-scoped — which is exactly what the trigger now prevents.

### `account_activity`

The settings page shows users what has changed in their account. This migration adds
**`public.account_activity`**: one row per event, with `user_id` (→ `auth.users`, `ON DELETE
CASCADE`, so the history goes with the account), a dotted `event_type` such as
`profile.updated`, a JSON object `details` (what changed) and a server-set `occurred_at`.
The catalogue of event types and the shape of each `details` is defined by the application in
`src/infrastructure/account-activity/events.ts`; the database only enforces the format of
`event_type`, that `details` is an object, and a 4 KiB bound on it.

What the database guarantees:

- **Users read their own rows only.** RLS is enabled with a single `SELECT` policy
  (`user_id = auth.uid()`); `authenticated` holds `SELECT` and nothing else; `anon` nothing.
- **Nobody writes to the table.** No role — not even `service_role` — holds `INSERT`, `UPDATE`
  or `DELETE`, and there is no policy for them. The identity sequence is not reachable either.
- **One append-only write path:** `public.record_account_activity(p_user_id, p_event_type,
p_details)`, a `SECURITY DEFINER` function executable by `service_role` alone. The
  application calls it with the service-role client from
  `src/infrastructure/account-activity/record-account-activity.ts`, passing the id of the user
  whose session the Server Action has already verified.

Why the service role: a Server Action authenticated with the user's cookies presents the
**same JWT the browser holds**. Anything executable by `authenticated` — a direct `INSERT` or
an RPC that fills in `auth.uid()` — would therefore be callable from the browser through
`/rest/v1/rpc`, and a user could plant fake entries in their own history. The service-role key
is the only server-only credential.

Reads are paged by keyset on `(occurred_at, id)` — the order the card shows — through the
`account_activity_user_recent_idx` index; the "load older" cursor the browser hands back is
an opaque token the server decodes strictly before use, and the read it drives runs as the
user under RLS.

Recording is best effort by design: it happens after the change it describes has been made (the
change lives in GoTrue's `auth.users`, so the two cannot share a transaction). A failure to
record is logged and never undoes or hides the change.

Verify on the hosted database after deploying:

```sql
select r.rolname,
       has_table_privilege(r.rolname, 'public.account_activity', 'SELECT') as can_select,
       has_table_privilege(r.rolname, 'public.account_activity', 'INSERT') as can_insert,
       has_table_privilege(r.rolname, 'public.account_activity', 'UPDATE') as can_update,
       has_table_privilege(r.rolname, 'public.account_activity', 'DELETE') as can_delete,
       has_function_privilege(r.rolname, 'public.record_account_activity(uuid, text, jsonb)', 'EXECUTE') as can_record
  from pg_roles r where r.rolname in ('anon', 'authenticated', 'service_role');
-- expected: anon all false; authenticated select only; service_role select + record only
```

### `rate_limits`

An invoice export can make up to a hundred Stripe requests, and nothing stopped a user — or a
script holding their session — from repeating it. The limit is kept in the database rather
than in memory so that every server instance (and every serverless cold start) shares it.

- **`public.rate_limits`** — one row per `(user_id, bucket)` (→ `auth.users`, `ON DELETE
CASCADE`) holding a single timestamp. `bucket` is a dotted lowercase name such as
  `export.invoices`. RLS is enabled with **no policy** and every privilege is revoked from the
  API roles: nobody can read, reset or forge an allowance through the REST API.
- **`public.consume_rate_limit(p_user_id, p_bucket, p_interval_seconds, p_burst)`** — the only
  way in (`SECURITY DEFINER`, `service_role` only). GCRA: `p_burst` requests at once, then one
  more every `p_interval_seconds`. Returns one row `(allowed, retry_after_seconds)`; a refused
  request consumes nothing and is told how long to wait (whole seconds, at least 1). The row
  is locked for the decision and the clock is read after the lock is held, so concurrent
  requests are decided one after another: N parallel requests never get more than the burst.
- **The application's policy** is `INVOICE_EXPORT_RATE_LIMIT` in
  `src/features/billing/services/collect-invoice-export.ts` (five at once, then one a minute),
  applied only once an export is about to call Stripe. It calls the function through
  `src/infrastructure/rate-limit/consume-rate-limit.ts` with the service-role client, and
  **fails closed**: if the allowance cannot be checked (function missing, database error) the
  export is refused with a 503 rather than sent to Stripe unchecked. Apply this migration
  before deploying the export.

Check after applying:

```sql
select r.rolname,
       has_table_privilege(r.rolname, 'public.rate_limits', 'SELECT') as can_select,
       has_table_privilege(r.rolname, 'public.rate_limits', 'UPDATE') as can_update,
       has_function_privilege(r.rolname,
         'public.consume_rate_limit(uuid, text, integer, integer)', 'EXECUTE') as can_consume
  from pg_roles r where r.rolname in ('anon', 'authenticated', 'service_role');
-- expected: every column false, except can_consume for service_role
```

Support can lift a user's limit at once as `postgres`:
`delete from public.rate_limits where user_id = '<uuid>' and bucket = 'export.invoices';`

## Assumptions about the existing `subscriptions` table

`public.subscriptions` predates this repository's migrations and is **not** managed here. Its
real definition could not be inspected while this migration was written. The functions assume
only what the application code already assumed:

- the table `public.subscriptions` exists;
- it has the columns `stripe_customer_id`, `stripe_subscription_id`, `status` and `"userId"`
  (that exact casing — it is what the application writes);
- **column types are not assumed.** Values are converted with
  `jsonb_populate_record(null::public.subscriptions, …)`, i.e. using the table's actual types.
  A value that does not fit (e.g. a non-UUID into a `uuid` column) fails the transaction, which
  the webhook reports as a 5xx.
- `"userId"` may be `NULL` until an event that identifies the user arrives (a
  `customer.subscription.created` usually precedes the `checkout.session.completed` that carries
  `metadata.userId`). If the column is `NOT NULL`, such inserts fail with a 5xx and Stripe
  retries; by the time of the retry the checkout event has normally linked the user. Consider
  propagating `metadata.userId` to the subscription (`subscription_data.metadata` at Checkout)
  so every event carries it — not done here to keep checkout behaviour unchanged.
- `status` receives Stripe's subscription statuses: `active`, `trialing`, `past_due`, `unpaid`,
  `incomplete`, `incomplete_expired`, `paused`, `canceled`. If `status` is a constrained enum or
  has a check constraint, all eight values must be allowed.
- No uniqueness constraint on `stripe_subscription_id` is assumed or required.

Function bodies are resolved at first execution (the integration tests verify this), so both
migrations apply even if `subscriptions` is missing or differs; the mismatch surfaces as an
error on the first webhook call (non-2xx → Stripe retries) rather than as silent data loss.
Verify before deploying:

```sql
select column_name, data_type, is_nullable, column_default
  from information_schema.columns
 where table_schema = 'public' and table_name = 'subscriptions';
select to_regclass('public.stripe_webhook_events');   -- must be NULL (name is free)
```

## Deploying

1. Install the CLI (`npm i -g supabase` or `brew install supabase/tap/supabase`) and log in:
   `supabase login`.
2. Link the repository to your project: `supabase link --project-ref <project-ref>`.
3. **If the project already has objects not described by migrations** (it does: `subscriptions`,
   auth config, …) capture a baseline first so the CLI's migration history matches reality:
   `supabase db pull` (creates `supabase/migrations/<ts>_remote_schema.sql`; review and commit
   it). Its timestamp will be newer than the idempotency migration; that is fine, the
   idempotency migration does not depend on `subscriptions` at apply time.
4. Review what will run: `supabase db push --dry-run`.
5. Apply: `supabase db push`.
6. Confirm privileges on the hosted database:
   ```sql
   select r.rolname, has_function_privilege(r.rolname,
     'public.stripe_apply_subscription_event(text,text,bigint,smallint,text,text,text,text)', 'EXECUTE')
     from pg_roles r where r.rolname in ('anon','authenticated','service_role');
   -- expected: anon=false, authenticated=false, service_role=true
   ```
7. Deploy the application. The webhook requires `SUPABASE_SERVICE_ROLE_KEY` at runtime.

Local development: `supabase start` applies all migrations to a local stack (Docker required).

### Rolling back

```sql
-- rate limits migration (invoice exports then fail with 503 until the application no
-- longer calls the function: deploy the previous version at the same time)
drop function if exists public.consume_rate_limit(uuid, text, integer, integer);
drop table if exists public.rate_limits;
-- account activity migration (the history is lost; the application then logs a failure
-- per profile change and otherwise keeps working)
drop function if exists public.record_account_activity(uuid, text, jsonb);
drop table if exists public.account_activity;
-- ownership migration (the table stays locked down only if you keep RLS; dropping the
-- policy without disabling RLS makes the table unreadable to users, which is the safer failure)
drop trigger if exists subscriptions_customer_owner on public.subscriptions;
drop function if exists public.subscriptions_enforce_customer_owner();
drop index if exists public.subscriptions_stripe_subscription_id_key;
drop policy if exists subscriptions_select_own on public.subscriptions;
-- alter table public.subscriptions disable row level security;  -- only if you really mean to
-- lifecycle migration
drop function if exists public.stripe_apply_subscription_event(text, text, bigint, smallint, text, text, text, text);
drop index if exists public.stripe_webhook_events_subscription_position_idx;
alter table public.stripe_webhook_events
  drop column if exists outcome, drop column if exists type_rank,
  drop column if exists event_created, drop column if exists stripe_subscription_id;
-- idempotency migration (re-create its functions from the file if only rolling back lifecycle)
drop table if exists public.stripe_webhook_events;
```

Rolling back the database while the new application code is deployed makes every webhook fail
with a 5xx (function missing) — deploy the previous application version at the same time.

## Operations

- **Retention.** The ledger grows by one row per applied event. Stripe retries for at most
  72 hours, so rows older than that are only useful for auditing. Prune periodically if
  desired, e.g. with `pg_cron`:
  `delete from public.stripe_webhook_events where processed_at < now() - interval '30 days';`
- **Duplicates** are logged by the webhook at `info` level (`duplicate delivery acknowledged`)
  and are expected after any retry.
- **`no_match`** deletions (no row for that subscription id) are acknowledged with a warning and
  are _not_ recorded, so a later resend can still apply once the row exists.
- **Account activity retention.** `public.account_activity` grows by one row per recorded
  change and is never pruned by the application (no role it uses may delete). If a retention
  period is wanted, prune as `postgres`, e.g. with `pg_cron`:
  `delete from public.account_activity where occurred_at < now() - interval '1 year';`
  Deleting a user (dashboard or admin API) removes their history through the foreign key.

## Testing

- `npm test` — unit tests with an in-memory mock of the functions' contract (no database).
- `npm run test:db` — integration tests against a **real PostgreSQL** server: applies all
  migrations to a throwaway database, then verifies privileges, lifecycle transitions,
  out-of-order and same-second ordering, terminal statuses, user association without metadata,
  duplicate and parallel delivery, advisory-lock blocking on in-flight transactions, rollback on
  failure and successful retry; and, for the ownership migration, per-user row visibility under
  RLS, denied writes, the unique index and owner trigger (including through the webhook
  function), idempotent re-runs, leftover-policy removal, and the absent-table, duplicate-rows,
  shared-customer and `"userId" text` variants; and, for the account activity migration, the
  per-role privileges on the table, sequence and function, owner-only reads under RLS, the
  format/size constraints, cascade on user deletion, and the application writer end to end; and,
  for the rate limits migration, the burst/refill/wait arithmetic in real time, per-user and
  per-bucket allowances, exactly-the-burst under 20 parallel requests (on a new and on an
  existing row), argument checks, privileges, cascade, and the application limiter end to end. Uses local
  `initdb`/`pg_ctl` if available (also as root: the throwaway server then runs as an
  unprivileged account, see `scripts/with-local-postgres.sh`), or set `TEST_DATABASE_URL` (e.g. the `supabase start` database:
  `postgresql://postgres:postgres@127.0.0.1:54322/postgres`).

## Email confirmation template (merged auth flow)

The registration flow in `src/app/auth/callback/route.ts` accepts the token-hash
verification link from `supabase/templates/confirmation.html` and retains a PKCE code
fallback. Local Supabase configuration in `supabase/config.toml` points to this template.
On a hosted Supabase project, copy the template into **Authentication → Email Templates →
Confirm signup**, allow-list `http(s)://<your-app>/auth/callback`, and configure the
matching site URL. The supplied `.env.local` values are placeholders, not credentials.

For the billing migration, the `subscriptions_customer_owner` trigger uses a
transaction-scoped advisory lock to serialize writes claiming one Stripe customer.
Review `WARNING` messages for legacy duplicate subscriptions and shared owners before
applying the migration to any hosted production data.

### `support_requests`

The Support Center (`/support`) stores user-submitted requests with server-derived ownership and default status. The migration enables own-only RLS, column privileges, validation and a five-per-hour request limit. Apply it with the existing migrations. Browser testing in demo mode uses an in-memory stand-in; use `npm run test:db` for PostgreSQL integration tests.
